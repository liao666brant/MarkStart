# MarkStart 发版

只在用户显式调用 `$release` 或明确要求运行此 Skill 时执行。不得根据“提交”“更新版本”等普通上下文自动触发。

## 发版流程

1. 读取仓库 `AGENTS.md`，检查当前分支、远端、工作区、暂存区和未跟踪文件。存在合并/变基冲突、未解决的钩子错误或没有可用远端时停止。
2. 确认本次发版范围。只暂存用户要发布的源码、配置和文档；排除密钥、`.env`、临时文件以及未被项目跟踪的构建产物。若改动混杂且无法安全区分，停止并让用户整理范围。
3. 读取 `manifest.json` 的 `version`，计算下一版本：只递增最后一个数字段并保持原有段数（例如 `1.249` → `1.250`）。MarkStart 的扩展版本以 `manifest.json` 为准，不要因发版顺手改动 `package.json` 或锁文件。
4. 展示将要执行的两次提交、版本变更、远端和分支，并在任何 `git commit` 或 `git push` 前取得用户明确确认。确认内容至少包括“确认发版、提交并推送”。
5. 有待提交改动时，按变更内容生成中文 Conventional Commit 消息，精确暂存后提交。没有改动时跳过第一笔提交，不创建空提交。
6. 只修改 `manifest.json` 的 `version`，解析 JSON 并确认新版本有效；然后单独提交：`chore(manifest): 版本号升至 <新版本>`。
7. 推送当前分支到其已配置的远端：优先使用上游跟踪分支；没有跟踪分支时使用 `origin`，禁止 `--force`。推送失败时停止，不重置已完成的提交。
8. 推送完成后检查工作区干净，并报告两笔提交（或跳过的第一笔）、版本号、推送目标和验证结果。

## 验证与失败处理

- 源码或构建入口有变更时，按仓库 `AGENTS.md` 的最低要求运行受影响的检查；发布前至少确认 `manifest.json` 可解析且版本已更新。
- 任一步骤失败立即停止，不自动回滚、不强推、不覆盖用户改动；保留已成功的本地提交并说明下一步。
- 不使用 `git add -A` 隐式收集敏感或无关文件，不修改远端历史。
